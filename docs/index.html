Where it looks

      
A lock file is a receipt. depguard reads all of them.

      
Every install leaves a record somewhere. The scan looks in the three places a malicious version can hide, and matches each exact version against the known-malicious database.

      

        

          
          
Every project

          
All lock files under your home directory: npm, pnpm, Yarn and Bun. Nested copies count, so a bad version buried three dependencies deep is still found.

          
~/work/**/package-lock.json

        

        

          
          
Global installs

          
Command-line tools you installed globally months ago and forgot about, including everything they pulled in.

          
$(npm root -g)

        

        

          
          
The download cache

          
Proof that a tarball was downloaded on this machine, and on which day, even if the project that asked for it is long gone.

          
~/.npm/_cacache

        

      

      

        

          
Exact versions only.

          
A false alarm would mean rotating every credential you own for nothing. Every database update is tested against known-clean versions and the most popular npm packages before it ships.

Questions

      
What people ask

      

        

          How do I check if my machine was affected by an npm supply-chain attack?
          
Run npx depguard-cli exposure. It reads every lock file under your home directory, your global installs and the npm download cache, and reports any exact version known to be malicious, where it is, and what to rotate. On a typical developer laptop it takes about 15 seconds.

        

        

          Was I affected by the debug and color compromise of September 2025?
          
Only if a project, a global install or your npm cache holds one of the hijacked versions, such as debug 4.4.2 or color 5.0.1. The command above checks all three at once. Other versions of those packages are not affected.

        

        

          Does depguard send my dependency list anywhere?
          
No. The scan runs against a database bundled with the package. Nothing about your projects leaves your machine.

        

        

          Will it flag clean versions of a package that was once compromised?
          
No. It only matches the exact versions listed in an advisory. Every database update is tested against known-clean versions and the most popular npm packages before it ships.

        

        

          What happens if it finds something?
          
It lists every place the malicious version appears, whether it is actually installed, whether it runs install scripts and when it was downloaded, followed by the steps to take. If the version only sits in a lock file and never reached your disk, it tells you that too.

        

        

          How is this different from npm audit?
          
npm audit looks at one project at a time, and only at what that project's lock file lists. depguard looks at every project on the machine, the packages you installed globally and the cache of everything npm has downloaded, in a single run.

Security

      
What depguard catches, and how

      
It downloads the package tarball and scans the actual source code for malware patterns, obfuscation, data exfiltration and behaviour that does not match the description. Every finding comes with a plain explanation.

    


    

      
Static code analysis

      
Beyond CVEs: reading the code

      

        
Malware detection
Eval of decoded payloads, reverse shells via net.connect, cryptocurrency mining pool URLs (stratum+tcp). Critical severity, blocked automatically.
Critical

        
Data exfiltration
JSON.stringify(process.env), Object.keys(process.env), fetch with dynamic URLs from env vars, bracket-notation env access to evade scanners.
Critical

        
Code execution
eval(), new Function(), child_process.exec and spawn, shell interpreter spawning. Dangerous patterns are flagged with context.
High

        
Obfuscation
Long hex or unicode-encoded strings, base64 payloads, minified source in non-.min.js files. Techniques used to hide malicious code from reviewers.
High

        
Behaviour mismatch
A "string formatter" that makes network calls? A "date utility" that reads the filesystem? depguard compares what a package says it does with what it actually does.
Unique

        
Rich explanations
Every finding includes severity, category, title, an explanation of why it is dangerous, the exact evidence from the source and a recommendation.
Developer-friendly

Guard. Audit. Review. Clean up.

          
The full AI coding lifecycle: verify packages before install, audit for vulnerabilities, review the code the AI wrote, and remove unused dependencies.

          

            
1. Guard
depguard_guard runs before every npm install. Blocks hallucinated packages, detects typosquatting, runs a security audit.
[BLOCK] ai-made-up-pkg
  Package does NOT exist on npm!

            
2. Audit
depguard_audit downloads the tarball, scans the source for malware, checks two advisory databases and analyses install scripts.
[WARN] expresss
  Possible typosquat of: express

            
3. Review
depguard_review finds the debris an AI agent leaves behind: console.logs, empty catch blocks, broken imports, orphan files, abandoned TODOs.
Found: 3 console.logs, 1 empty catch
  Fixing before commit...

            
4. Clean up
depguard_sweep finds packages that were installed but never imported, with estimated size savings.
Unused: lodash (~1.4 MB)
  Savings: ~2.4 MB from 3 packages
